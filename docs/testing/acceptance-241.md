## Scope Note

The branch rebuilds enabled plugins from the registry in every new plugin manager, records the
port and PID of a running gRPC plugin (`active_port`, `pid`) and attaches to that process from
later CLI processes. Plugins are started detached (`Setsid` / `DETACHED_PROCESS`), `Shutdown`
of the manager detaches instead of stopping, `plugin disable` clears the registry flag and
`assignPort` skips ports of other enabled plugins. The placeholder `proto/generated.go`, whose
`NewPluginServiceClient` returned `nil`, is replaced by code generated from `plugin.proto`.

**Test plugin**: up to retest 1 the template from `plugin create` did not implement the host
protocol (O4), so the gRPC plugin under test was the compiled unit test binary of
`src/app/plugins/manager` (`go test -c`, enabled by `PORTUNIX_TEST_GRPC_PLUGIN=1`), which serves
the real `PluginService`, installed with the manifest generated by `plugin create`. Retest 2
also uses a plugin generated by `plugin create` (O4 fixed).

**Independence note**: the code on the branch was written by the same Claude Code session in
the developer role before testing.

**Not covered**:

- Windows and macOS — the code cross-compiles and vets, nothing was executed
- Java and Python gRPC plugins — only native plugins were started
- A plugin generated by `plugin create` in the first run and retest 1 — covered in retest 2

## Defects

### D1: Concurrent `plugin start` can orphan the plugin process — major, fixed in `34d0a5d`

Two `portunix plugin start` commands for the same plugin, run at the same time, both see no
recorded PID and both start a process on the same port. The losing process fails to bind and
exits, but its CLI still connects to the port, which the winner serves, so both commands report
success. Whichever command writes the registry last wins; in 3 of 10 runs that was the PID of
the dead process. `plugin stop` then answers `plugin t241-a is not running`, and the real plugin
keeps running and holds the port until it is killed by hand.

Reproduction:

```bash
portunix plugin start t241-a & portunix plugin start t241-a & wait
portunix plugin stop t241-a   # Error: ... is not running; plugin process still alive
```

Root cause: `GRPCPlugin.Start` does not check that the child it started is the one that
answers on the port. Suggested fix: fail the start when the child has exited (`p.exited`
closed) before or right after the gRPC connection is made. Watching `p.exited` while dialing
also lets a crashing plugin fail at once (O1). A cross-process lock around `StartPlugin` would
also prevent the second process from being spawned.

Retest: R-F10 passes 20 of 20; the lock serializes the starts.

### D2: Plugins README still lists `generated.go` — minor, fixed in `34d0a5d`

`src/app/plugins/README.md:63` and `README.cs.md:63` list `proto/generated.go`, which the branch
deletes. They should list `plugin.pb.go` and `plugin_grpc.pb.go` generated from
`plugin.proto`.

Retest: R-S3 passes.

### D3: `registry.json` is written in place, concurrent readers see an empty file — major, fixed in `d830eb8`

`Registry.save` (`src/app/plugins/manager/registry.go`) truncates `registry.json` with
`os.Create` and then writes the JSON. Every Portunix command loads the registry in
`NewRegistry` without the new lock, so a command that runs while another process saves can
read an empty or partial file:

```text
Error: failed to initialize plugin manager: failed to create registry: failed to load registry: EOF
```

R-F12 shows it 3 times in 8947 `plugin list` runs. The same write exists on `main`, but #241
makes concurrent commands a supported case and its own concurrent test runs into it (D4). A
crash during the write would also leave a broken registry.

Suggested fix: write to a temporary file in the same directory and rename it over
`registry.json` (atomic on POSIX; on Windows `os.Rename` replaces the file, a reader holding it
open can make it fail, so retry briefly).

Retest: R2-F12 passes with 0 failures in 44 577 reads; R2-U3 passes.

### D4: The concurrent start test hangs instead of failing — major, fixed in `d830eb8`

`TestConcurrentStartLeavesOneStoppableProcess` calls `cliManager` in its own goroutines.
`cliManager` uses `t.Fatal`, which in a goroutine other than the test only ends that goroutine,
so nothing is sent on `errs` and the test blocks until the `go test` timeout (10 min by
default). D3 triggers it: `NewManager` fails on the empty registry. In CI this is an
intermittent 10 min hang, and the hung test leaves its plugin process running.

Suggested fix: create the managers in the goroutines without `t.Fatal` and send the
`NewManager` error on the channel; register a cleanup that kills the recorded plugin process
before the test can block, or wait on the channel with a timeout.

Retest: R2-U2 finishes in 53 s; with D3 injected again the test fails at once instead of
hanging (R2-U6).

### D5: A symlinked `registry.json` is replaced by a regular file — minor, fixed in `3042a03`

The D3 fix writes `.registry-*.tmp` next to `registry.json` and renames it over the path. When
`~/.portunix/plugins/registry.json` is a symlink, for example into a dotfiles repository, the
rename replaces the symlink itself. Portunix keeps working with the new regular file, but the
symlink target is no longer updated and the user's setup is silently broken. On `main` the file
was rewritten in place, which follows the symlink.

Suggested fix: resolve the path with `filepath.EvalSymlinks` before writing, create the
temporary file in the directory of the resolved target and rename it over the target.

Retest: R3-E2 and R3-F12 pass; the symlink stays and its target is updated.
