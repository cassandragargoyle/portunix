# Issue #241: plugin start/stop/health fail with "not enabled" after plugin enable for gRPC plugins

**Status**: ✅ Implemented
**Priority**: Medium
**Type**: Bug
**Component**: portunix
**Created**: 2026-10-25
**Completed**: 2026-10-26
**GitHub**: #241
**Related**: #156, #232

## Summary

`portunix plugin enable <name>` reports success, but every following `plugin start`,
`plugin stop` and `plugin health` of a gRPC plugin fails with `plugin <name> is not enabled`.
A gRPC plugin can therefore not be started through the CLI at all. Found while testing #232
(`docs/testing/acceptance-232.md`, defect D3). The behaviour is the same on `main` before #232.

## Problem Description

Reproduction with a plugin generated from the template:

```bash
portunix plugin create t232-grpc -o /tmp/plug
cd /tmp/plug/t232-grpc && go mod tidy && go build -o t232-grpc .

portunix plugin install /tmp/plug/t232-grpc   # ✅ Plugin installed successfully!
portunix plugin enable t232-grpc              # ✅ Plugin enabled successfully!
portunix plugin start t232-grpc               # Error: failed to start plugin: plugin t232-grpc is not enabled
portunix plugin health t232-grpc              # Error: ... plugin t232-grpc is not enabled
portunix plugin stop t232-grpc                # Error: failed to stop plugin: plugin t232-grpc is not enabled
```

`plugin list` and `plugin info` show the plugin as `stopped`.

### Root Cause

`Manager.EnablePlugin` (`src/app/plugins/manager/manager.go`) does two things:

1. Creates a `GRPCPlugin` instance and stores it in the in-memory map `Manager.plugins`
2. Marks the plugin as enabled in the registry file (`Registry.EnablePlugin`)

`StartPlugin`, `StopPlugin`, `DisablePlugin` and the health lookup check only the in-memory
map. `NewManager` creates an empty map and never fills it from the registry, so in a new CLI
process every enabled plugin looks disabled. The registry flag `Enabled` is written but never
read for this purpose.

#156 fixed `plugin health` for helper (CLI) plugins only; gRPC plugins are still affected.

## Proposed Approach

When the manager is created, or lazily on the first lookup, build the plugin instance for every
plugin that is marked `Enabled` in the registry, the same way `EnablePlugin` does. A running
plugin started by an earlier CLI process also needs to be found again (PID or port stored in
the registry), otherwise `plugin stop` cannot stop it.

## Acceptance Criteria

1. After `plugin enable`, `plugin start` in a new CLI process starts the gRPC plugin
2. `plugin health` of a running gRPC plugin reports its state through gRPC
3. `plugin stop` in a new CLI process stops a plugin started by an earlier process
4. `plugin disable` in a new CLI process disables an enabled plugin
5. Helper (CLI) plugins keep working as after #156
6. Unit tests cover the reload of enabled plugins from the registry

## Testing

- Plugin generated by `plugin create`, run in a throwaway home directory (`HOME` set to a
  temporary directory) so the real plugin registry is not touched
- Full lifecycle: install, enable, start, health, a gRPC call, stop, disable, uninstall — each
  command in its own process
- Regression: `plugin list`, `plugin health` of a helper plugin
